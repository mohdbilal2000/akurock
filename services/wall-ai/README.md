# Wall AI — segmentation + metric depth for the visualizer

A small FastAPI service that turns a room photo into a measured wall:

```
POST /detect  (multipart: photo, optional tap_x/tap_y)
  -> 4 wall corners in the photo's own pixels
  -> the wall's real width and height in millimetres
  -> a wall mask and an occluder mask (PNG data URLs)
  -> a confidence the client uses to decide whether to trust any of it
```

The Next.js app never calls this directly from the browser: it proxies
through `app/api/detect-wall`, which holds the URL and the shared secret.

## Why two models

| Stage | Model | What it buys |
| --- | --- | --- |
| Segmentation | `nvidia/segformer-b2-finetuned-ade-512-512` | Which pixels are *wall*, and which are sofa/door/radiator/art standing in front of it |
| Metric depth | `depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf` | The wall's size **in metres**, from one photo |

Segmentation alone gives an outline but no scale, which is why the old tool
had to ask for a wall height. Metric depth removes the question: the wall
mask's pixels are back-projected to 3D, RANSAC fits the plane they lie on,
and the wall is measured in its own plane. That is what makes the panel
count on screen an orderable number rather than a guess.

The occluder mask is the other half of the realism: panels render *behind*
whatever is in front of the wall, so a plug socket and its cable stay on
top of the render instead of being painted over.

Both are swappable without code changes — `WALL_AI_SEG_MODEL` /
`WALL_AI_DEPTH_MODEL`. Class semantics come from the model's own
`id2label`, so any ADE20K-trained head works (Mask2Former, OneFormer, B0-B5).

## Running it locally

```bash
cd services/wall-ai
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

Then point the Next.js app at it:

```bash
# .env.local
WALL_AI_URL=http://localhost:8000
```

First request downloads ~350MB of weights into the HF cache and takes a
minute or two; after that a 1024px photo is ~2-4s on a laptop CPU.

## Tests

```bash
pytest            # 33 tests, no model weights needed
```

The maths (plane fitting, metric extents, corner ordering, mask rules) is
tested against synthetic scenes built in 3D and projected through known
intrinsics — a wall of a known size has to come back that size, including
when it is photographed at 35 degrees off-axis.

`tests/test_detect_endpoint.py` goes further and drives `POST /detect` with
the two model calls stubbed by a synthetic room (wall, floor, one sofa, a
plane at 3m): everything between the models and the JSON the browser
consumes is covered, including that a 500px-tall wall at 3m comes back as
~2.48m. The model calls themselves are isolated in `app/inference.py`, so
nothing in the test path imports torch.

## Deployment

`render.yaml` at the repo root declares this as a **private** service
(`type: pserv`), reachable only by the Next.js app over Render's internal
network, with the shared secret generated by Render and injected into both.

Sizing: torch plus both models sit at roughly 1.5GB resident. A 512MB
instance survives start-up and then OOMs mid-inference, which presents as a
hang — use 2GB or larger. `WALL_AI_ENABLE_DEPTH=0` halves the footprint at
the cost of metric measurement (the client falls back to its wall-height
slider and says so in the UI).

The Dockerfile bakes the weights into the image on purpose. Downloading
them on first request instead means the first visitor after every deploy
waits minutes, and a cold start that races a health check fails outright.

## Configuration

| Variable | Default | Notes |
| --- | --- | --- |
| `WALL_AI_SEG_MODEL` | `nvidia/segformer-b2-finetuned-ade-512-512` | B0 for speed, B4/B5 for accuracy |
| `WALL_AI_DEPTH_MODEL` | `depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf` | Must be a **metric** model; a relative-depth model makes the measurements meaningless |
| `WALL_AI_ENABLE_DEPTH` | `1` | `0` disables measurement and halves memory |
| `WALL_AI_MAX_SIDE` | `1024` | Inference resolution; masks come back at this size, corners in the photo's own pixels |
| `WALL_AI_API_KEY` | unset | When set, `X-API-Key` must match |
| `WALL_AI_DEVICE` | `cpu` | `cuda` if a GPU is ever attached |
| `WALL_AI_WARM_ON_START` | `0` | Load weights at boot instead of on first request |

## Privacy

Photos are processed in memory and never written to disk, logged, or
forwarded. Nothing about a request is retained after the response is sent —
which is what the visualizer's privacy line now promises.

## Degrading instead of failing

Every stage has a fallback, because a visualizer that refuses to open is
worse than one that asks for a little help:

| Situation | What happens |
| --- | --- |
| Depth model disabled or fails | Quad from the mask outline, wall size assumed (2.5m), flagged in the UI |
| Wall isn't one flat plane (inliers < 45%) | Same fallback, flagged |
| Confidence below 0.45 | Client opens on the corner-adjust step instead of the finished render |
| No wall found | 422; client falls back to its on-device edge heuristic |
| Service down or unreachable | 503 from the proxy; client falls back to manual corners, unchanged from before this service existed |
